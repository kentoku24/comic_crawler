# Issue Draft: GHCR の新バージョン検知と自動デプロイの仕組みを作る

## 要求の要約
GitHub Container Registry (GHCR) 上のコンテナイメージに新しいバージョンが公開されたことを検知し、現在運用している環境へ自動でデプロイする仕組みを導入したい。
対象は個人運用（日曜大工）プロジェクトであり、**シンプルさ**・**一般的な技術**・**長期運用のしやすさ**を最優先にする。

## 解決したい課題
- 手動での更新確認とデプロイ作業が負担になり、更新漏れや反映遅延が起こる。
- 1人運用のため、複雑な運用基盤を入れると将来メンテナンスコストが高くなる。
- 更新失敗時の切り戻しや通知が曖昧だと、障害時の対応が遅れる。

## 目的
- GHCR の新バージョン公開を自動検知し、デプロイまでを自動化する。
- 運用手順をできる限り少なくし、個人でも長期的に保守可能な状態にする。
- 失敗時にすぐ気づける最低限の監視・通知・ロールバック導線を用意する。

## 対象ユーザー / 関係者
- 主担当: リポジトリオーナー（1名）
- 関係者: 必要に応じてリポジトリ閲覧者（将来的な引き継ぎ候補）

## スコープ
- GHCR の新イメージ（または tag）公開イベントをトリガーにした自動デプロイフローの定義
- 現行実行環境での安全な再デプロイ手順（pull → apply/restart → health check）
- 失敗検知・通知・切り戻し導線の最小構成
- 導入後の運用手順書（更新方法、停止方法、障害対応、手動介入方法）の整備

## 非スコープ
- マルチクラスタや高可用構成などの大規模運用向け機能
- カナリアリリースやブルーグリーン等の高度なデプロイ戦略（初期段階）
- 独自オーケストレータの開発や複雑な自作デプロイプラットフォーム

## 機能要件（たたき台）
1. GHCR 上の対象イメージ更新を定期またはイベントで検知できること。
2. 新バージョン検知時にデプロイジョブが自動実行されること。
3. デプロイ後に最低1つのヘルスチェックで正常性を判定できること。
4. 失敗時は通知され、手動で再試行/ロールバックしやすいこと。
5. どのバージョンがいつ反映されたかをログで追跡できること。

## 非機能要件（たたき台）
- **シンプル性**: 構成要素を最小限にし、依存サービスを増やしすぎない。
- **可搬性**: 一般的なツール（例: GitHub Actions / Docker Compose / systemd など）中心で構築する。
- **保守性**: 半年後に見返しても理解できる設定・手順にする。
- **信頼性**: 更新失敗時に検知でき、復旧手順が明文化されている。
- **セキュリティ**: GHCR 認証情報・デプロイ鍵・Webhook シークレットを安全に管理する。

## 制約条件
- 1人運用で、運用負担を増やす複雑構成は避ける。
- 可能な限りマネージド/一般的な仕組みを使い、独自実装を減らす。
- 既存環境への影響を最小化し、段階導入できること。

## 前提
- 対象コンテナイメージは GHCR に push される運用がすでにある（または導入予定）。
- 現行環境にはコンテナ再起動/更新を実行可能な手段がある。
- GitHub 側で Actions / Secrets / Webhook 等を利用できる。

## 受け入れ条件（案）
- [ ] GHCR に新しい対象バージョンを push すると、一定時間内に自動デプロイが実行される。
- [ ] デプロイ成功時に反映済みバージョンを確認できる（ログ/状態表示）。
- [ ] デプロイ失敗時に通知され、手順書に従って復旧できる。
- [ ] 手動デプロイ手順（緊急時フォールバック）が文書化されている。

## 実装候補（比較対象）
- 案A: GitHub Actions（GHCR publish トリガー） + SSH でデプロイ先更新
- 案B: デプロイ先で定期ポーリング（GHCR tag 確認） + ローカル更新スクリプト
- 案C: Watchtower 等の自動更新ツール導入（必要最小限の設定）

> 本 issue では「どれを採用するか」までを決める。初回は最もシンプルで rollback しやすい案を優先する。

## 未確定事項 / 要確認事項
1. デプロイ先の実行基盤（Docker Compose / systemd / 単体 Docker / その他）は何か。
2. 更新トリガーは push イベント駆動か、定期ポーリングか、どちらを優先するか。
3. 許容ダウンタイム（無停止が必要か、数十秒の再起動許容か）。
4. 通知先（Discord / Slack / メール / GitHub 通知）の優先度。
5. ロールバック方式（直前 digest 固定で戻す、手動のみ、など）。
6. バージョン指定方針（latest 禁止、semver tag、digest pinning など）。

## リスク
- `latest` 運用のみだと、想定外更新の追跡や切り戻しが困難。
- 自動デプロイだけ先行すると、失敗検知が弱く障害に気づきにくい。
- デプロイ先依存の手順（Compose/systemd 差分）を吸収しないと運用ドキュメントが形骸化する。

## 次に決めるべきこと
1. デプロイ先基盤の確定
2. 更新トリガー方式の確定（イベント vs ポーリング）
3. 最小通知経路とロールバック手順の確定
4. 採用案を 1 つに絞った PoC 範囲の定義
