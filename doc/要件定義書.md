# 要件定義書

## 1. 背景

`comic_crawler` は、複数の漫画サイトを監視し、更新があった作品を Discord 上で通知し、保存済みの最新状態を参照できる仕組みである。  
現在の仕様書には、要件、設計、実装制約、運用手順、テスト条件が混在しており、受け入れ担当・実装担当・レビュー担当の間で「何を満たせば受け入れ可能か」の判断軸が揃いにくい状態にある。

また、本システムは AI を前提に開発・運用されるため、仕様は単に詳細であるだけでなく、観測可能で、判断可能で、テスト可能である必要がある。  
特に Discord 上での読みやすさ、同一話の重複通知防止、障害時の復旧しやすさ、および state の安全性は、継続運用上の重要度が高い。

本要件定義書は、受け入れ条件の明文化を主目的として、何を満たすべきかを整理する。  
実現方式や内部構造の詳細は、別紙の設計書で定義する。

---

## 2. 解決したい課題

現時点で解決したい主要な課題は以下である。

1. 仕様書に複数のレイヤが混在しており、受け入れ条件が不明瞭である  
2. Discord 上の通知が重要な利用面であるにもかかわらず、可読性や誤解防止の観点が整理されていない  
3. 「更新なし」と「run 失敗」や「通知失敗」が利用者から区別しづらい  
4. 同一話の再通知を確実に防ぎたい  
5. 異常終了や同時実行が起きても state を壊したくない  
6. AI 主体の開発運用に耐えるよう、主要要件を自動試験で判定可能にしたい  

---

## 3. 目的

本件の目的は以下とする。

- `comic_crawler` の外部契約を明確にする
- 受け入れ条件を明文化する
- 受け入れ担当・実装担当・レビュー担当が同じ判断基準を持てる状態にする
- 内部設計と外部契約を切り分け、変更しやすい部分と固定すべき部分を分離する
- 主要要件を自動テストで確認可能にする

---

## 4. 対象システムの概要

対象システムは、複数の漫画作品を監視し、新しいエピソードの公開を検知して Discord へ通知する。  
また、保存済み state をもとに、Discord 上で現在の最新話一覧を read-only に参照できる。  
運用上は、定期実行と手動実行の両方をサポートし、通知結果および実行結果を可視化する。

---

## 5. 対象ユーザー / 関係者

### 5.1 受け入れ担当
- 本要件を満たしているか最終判断する担当
- 主に観測可能な挙動と受け入れ条件を評価する

### 5.2 実装担当
- 要件と設計に基づいて機能を実装する担当
- 外部契約を満たす範囲で内部実装を選択する

### 5.3 レビュー担当
- 要件、仕様、設計、テスト観点の妥当性を確認する担当
- 曖昧さや漏れ、矛盾を指摘する

### 5.4 Discord 通知の受信者
- Daily notification や `latest` 応答を読む利用者
- 主に携帯端末上で内容を確認する

### 5.5 将来の運用担当 / 保守担当
- 障害対応、delivery failure 確認、ログ確認、継続運用を担当する

## 6. スコープ

今回の要件定義で対象とする範囲は以下とする。

### 6.1 外部契約
- Discord `latest` query
- Discord `fetch` trigger
- Daily notification
- run report

### 6.2 データ前提
- watchlist v2
- state v2
- v2 を正とする runtime 契約

### 6.3 品質要件
- state 安全性
- 同一話の再通知防止
- delivery failure 時の可視化
- 最低限のセキュリティ要件
- 最低限の性能目標
- 自動テストで判定可能な受け入れ条件

## 7. 非スコープ

今回の要件定義では、以下は対象外とする。

- migration / rollback の手順
- v1 互換性
- v1 / v2 混在運用
- Status CLI の受け入れ仕様
- Backlog CLI の受け入れ仕様
- retry / backoff の具体アルゴリズム
- CLI 文面の細部固定
- metadata 更新誤通知の高度な改善
- 内部設計品質そのものの評価
- 将来の source 追加や大規模機能拡張

## 8. 成功条件

本件が成功したと見なせる条件は以下とする。

### 8.1 受け入れ条件の明確化
- 何が必須条件で、何が目標値かが区別されている
- 受け入れ担当・実装担当・レビュー担当が同じ観点で判断できる

### 8.2 主要 UX の明確化
- `latest` と Daily notification の文面契約が整理されている
- Discord 上で読みやすく、誤解を招きにくい

### 8.3 運用品質の明確化
- run report により「更新なし」と「失敗」が区別できる
- delivery failure が隠れない
- state 破損が受け入れ NG として明確に扱われる

### 8.4 テスト可能性
- 主要要件が自動テストで検証可能である
- モックベースの自動試験を受け入れ主判定にできる

## 9. 優先順位

本件における優先順位は以下とする。

### 最優先
- state を壊さないこと
- 異常終了や同時実行時にも JSON として読める状態を保つこと
- reader が読めない状態を作らないこと

### 次点
- Discord 上での可読性
- `latest` と Daily notification の見やすさ
- モバイル端末での確認しやすさ

### 次点
- 同一話の再通知防止
- `work_id + latest_key` 基準での重複防止

### 次点
- 障害時の可視化
- run report による状態把握

### 相対的に優先度が低いもの
- 高度な通知制御
- metadata 改善時の誤通知抑制の高度化
- CLI 文面の厳密固定
- retry / backoff の細かい実装方式

---

## 10. 機能要件

### 10.1 `latest` query
- 保存済み watchlist/state v2 のみを参照する
- read-only である
- live crawl を起動しない
- watchlist 順で結果を返す
- `enabled=false` の作品は既定で一覧に含めない
- orphaned state entry は一覧に含めない
- 未取得状態を未取得と分かる形で返す
- stale や部分失敗があっても自動実行に切り替えない

### 10.2 Daily notification
- 更新があった run のみ送信する
- 更新 0 件の run では送信しない
- 更新対象はその run で `latest_key` が変化した作品のみとする
- metadata の改善のみは通知しない
- 同一話の再通知防止は `work_id + latest_key` を基準とする
- 複数更新は 1 通に集約してよい
- watchlist 順で並ぶこと

### 10.3 `fetch` trigger
- Discord から手動で 1 回 run を起動する
- write path である
- 通常 run と同じ検知・通知・report 契約に従う
- 既存 run 実行中の追加 `fetch` は reject する
- reject 時は利用者が再試行すべきことを理解できる
- state 破損は許容しない
- 利用者が結果確認先を理解できること

### 10.4 run report
- 毎 run 送る
- 少なくとも以下を区別可能にする
  - 更新がなかった
  - run が失敗した
  - 更新はあったが delivery に失敗した
- 実行時刻、trigger source、更新件数、通知送信有無、failure 要約、状態要約が読み取れること

### 10.5 delivery visibility
- delivery failure は更新なしと混同されない
- delivery failure は run report などで可視化される
- delivery は best effort とし、失敗通知の durable な再送は要求しない

---

## 11. 非機能要件

### 11.1 可用性 / 耐障害性
- 異常終了しても state は JSON として壊れないこと
- 予期せぬ重複起動が起きても reader が読めない状態を作らないこと
- state 破損は受け入れ NG とする

### 11.2 可読性 / UX
- Daily notification と `latest` は携帯端末での可読性を優先する
- 行構造、情報順、表記ルールを固定する
- 文面は完全一致ではなく、構造一致で受け入れ判定できること

### 11.3 セキュリティ
- token をログに出さない
- webhook URL をログに出さない
- token / webhook URL を run report に出さない
- エラー出力にも秘匿情報を含めない

### 11.4 性能
- watchlist 100 件で 30 秒以内を目標とする
- Discord 初期応答は `latest` / `fetch` ともに 3 秒以内を目標とする
- `latest` の本応答は 10 秒以内を目標とする
- `fetch` の完了は 100 件 / 30 秒以内を目標とする
- これらは現時点では必達条件ではなく目標値とする

### 11.5 テスタビリティ
- 主要要件は自動テストで判定可能であること
- `latest` / Daily notification / run report はモックベースで検証可能であること
- Discord 実機確認は補助的な自動検証として用意できることが望ましい

---

## 12. 制約条件

- runtime baseline は Python 3.12 系とする
- runtime が正とする永続データは watchlist v2 / state v2 のみとする
- `latest` と Daily notification は固定度の高い外部契約として扱う
- run report は意味重視で扱い、細部文面は固定しない
- Discord 実機確認は主たる受け入れ判定ではなく補助検証とする
- 内部設計品質は別途評価し、本要件の主対象としない

---

## 13. 前提

- migration は完了済みである
- 今後の runtime は v2 前提で運用する
- AI が開発・運用に関与するため、曖昧さよりも判定可能性を優先する
- 観測可能な契約は SPEC.md に定義し、内部実現は設計書に定義する
- モックベース自動試験を受け入れ主判定とする

---

## 14. リスク

- run 中の `fetch` reject 制御が不十分だと利用者が挙動を誤解する可能性がある
- 文面を完全一致ではなく構造一致で判定するため、テスト設計が弱いと見た目劣化を見逃す可能性がある
- 性能値が目標値止まりのため、性能劣化が即時に NG 判定されない可能性がある
- 実機確認を補助検証に留めるため、Discord 実表示差異の検知が遅れる可能性がある
