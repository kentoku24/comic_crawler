# 仕様価値と維持コスト

## 1. 目的
この文書は、現行 Spec を「何の価値を守っているか」と「そのためにどれだけ実装・運用コストを払っているか」で棚卸しするための補助資料である。

狙い:
- 提供価値に対して重すぎる Spec を見つける
- 外部契約として守るべき Spec と、内部都合で複雑化している Spec を分ける
- 削除、緩和、統合の候補を順序付きで議論できるようにする

---

## 2. 見方
各 Spec を以下の 3 軸で見る。

- 価値
  - 利用者や運用者が直接得る価値の大きさ
  - 5 が最重要、1 が補助的
- 維持コスト
  - 実装分岐、状態管理、再送、整合性維持、テスト、運用手順を合わせた重さ
  - 5 が最も重い
- 契約固定度
  - 要件書で外部契約として固定されている強さ
  - 5 が強く固定、1 が内部都合に近い

判断の目安:
- 価値が高く、維持コストが低いものは維持
- 価値が高く、維持コストが高いものは簡略化して維持
- 価値が低く、維持コストが高いものは削除または緩和候補
- 契約固定度が低いものほど、内部改善で削りやすい

## 4. 採用する削減方針

### 4.1 `unread` と `history` を削除する
理由:
- 現状の通知経路は `unread` を消費していない
- `unread` は backlog / mark-read のための別レイヤであり、新着通知の必須要件ではない
- 要件定義書では Backlog CLI 自体が非スコープであり、外部契約としての固定度が低い
- `history` も最新通知の外部契約に必須ではない

削ると減るもの:
- `history` と `unread` の整合管理
- mark-read 系の概念負債
- docs 上の説明負荷

採用方針:
- `unread` を削除する
- `history` も削除し、state は `latest` と `health` に絞る

### 4.2 delivery retry/replay を捨てて best effort にする
理由:
- delivery failure の可視化自体は高価値
- ただし「後から確実に再送できる」まで守ると pending state、replay、dedupe、運用手順が一気に増える
- さらに今は generic と Discord で再送状態が二重化している

採用方針:
- best effort + run report 可視化に留める
- manual replay を削除する
- durable な pending state を持たない

### 4.3 `fetch` 同時実行許容をやめる
理由:
- 利用者価値は限定的
- state 安全性との組み合わせで実装負荷が重い
- 競合時の説明も難しい

採用方針:
- 同時 `fetch` は reject する
- 単一の run だけを write path に入れる

### 4.4 話数差分推定を削除する
理由:
- 便利ではあるが中核価値ではない
- タイトル解釈に依存するため、将来の source 差異で壊れやすい

採用方針:
- 話数差分推定は Spec から削除する
- 「gap」は仕様差分を指す用語としてのみ扱い、話数差分には使わない

### 4.5 notification policy を mode のみに縮小する
理由:
- 使われていなければ分岐コストだけが残る
- 作品単位の `mode` だけで十分な可能性がある

採用方針:
- `allowed_update_types` を廃止して `mode` のみ残す

---

## 5. 維持すべき中核 Spec
以下は価値が高く、削るより守る方がよい。

- state JSON 安全性
- `work_id + latest_key` による重複防止
- `latest` は保存済み state の read-only 参照であること
- Daily notification と run report の基本契約
- run report で failure 種別が見えること

これらは「何を提供するシステムか」を支える核であり、削るより簡潔に守る方向がよい。

---

## 6. 今回決めた整理
次の 5 点を今回の採用方針とする。

1. `unread` / `history` を state から外す
2. delivery retry / replay を削除する
3. `fetch` 同時実行を reject に変更する
4. 話数差分推定を削除する
5. notification policy を mode のみに縮小する

この 5 点を決めるだけで、state、delivery、運用 docs、テストの複雑さはかなり減らせる見込みがある。
