# 運用手順書

## 1. 目的

本手順書は、`comic_crawler` の日常運用、手動実行、障害確認、再送確認、Discord 表示確認、およびデバッグ時の基本手順を定義する。  
本手順書は、受け入れ仕様書（`SPEC.md`）および設計書で定義された契約と設計に基づき、運用担当が迷わず確認・切り分け・再実行できる状態を作ることを目的とする。

本手順書の対象は以下とする。

- 定期実行の確認
- `latest` の利用
- `fetch` の利用
- run report の確認
- delivery failure の確認と再送
- state 異常時の確認
- デバッグの基本手順
- Discord 実機確認の補助手順

---

## 2. 運用の前提

- runtime が正とする永続データは watchlist v2 / state v2 のみとする
- `latest` は read-only の参照機能であり、更新取得の代替ではない
- 更新検知は定期 run または `fetch` により行う
- Daily notification は更新があった run のみ送信される
- run report は毎 run 送信される
- state 安全性は最優先であり、異常時は state 破損有無を先に確認する
- Discord 実表示確認は補助的確認であり、主たる品質確認は自動試験を前提とする

---

## 3. 日常運用の確認ポイント

日常運用では、少なくとも以下を確認対象とする。

1. 定期 run が継続していること  
2. run report が継続して届いていること  
3. 更新があった日に Daily notification が届いていること  
4. 「更新なし」と「失敗」が run report 上で区別できること  
5. delivery failure が隠れていないこと  
6. `latest` が保存済み状態を正しく返していること  

---

## 4. 起動と定期実行

## 4.1 起動確認

起動後は以下を確認する。

- プロセスが起動している
- watchlist v2 / state v2 が読み込めている
- 定期スケジュールが有効である
- 初回 run または次回 run が予定どおりである
- 秘匿情報がログに露出していない

### 確認観点
- 起動直後に configuration error が出ていないか
- state load error が出ていないか
- run report が送信される状態か
- Discord adapter が初期化できているか

---

## 4.2 定期実行の確認

定期実行は以下の観点で確認する。

- 一定周期で run report が届く
- 更新がない場合も run report が届く
- 更新がある場合は Daily notification と run report の両方が届く
- failure 時にも run report 側で失敗が可視化される

### 異常の兆候
- run report が途切れる
- 毎回 failure になっている
- Daily notification が出ないのに run report に更新ありと出る
- 同一話の通知が繰り返される
- `latest` と run report の整合が取れない

---

## 5. `latest` の使い方

## 5.1 目的

`latest` は保存済み state の一覧を確認するための read-only コマンドである。  
live crawl は起動せず、watchlist/state を変更しない。

---

## 5.2 基本手順

Discord 上で、本文がちょうど以下になるメッセージを送る。

```text
latest
```

期待される結果
	•	保存済みの最新話一覧であることが分かる応答が返る
	•	最終巡回時刻が表示される
	•	現在の一覧が watchlist 順で表示される
	•	URL がある作品は link 形式になる
	•	未取得作品は未取得と分かる表示になる

⸻

5.3 latest の見方

確認ポイントは以下とする。
	•	応答が「保存済み一覧」であることが分かるか
	•	最終巡回時刻が極端に古くないか
	•	一覧順が watchlist 順になっているか
	•	同じ作品が重複表示されていないか
	•	未取得作品が誤って通常作品のように見えていないか
	•	一部 failure がある場合、その旨の warning が付いているか

⸻

5.4 latest に関する注意点
	•	latest は「更新なし」を意味しない
	•	latest は保存済み state の参照であり、更新確認そのものではない
	•	stale だからといって自動で最新取得が走るわけではない
	•	latest が失敗しても、それ自体は定期 run の失敗を意味しない
	•	latest の不整合を見つけた場合は、まず run report と state を確認する

⸻

6. fetch の使い方

6.1 目的

fetch は、その時点で 1 回だけ run を手動起動するための trigger である。
定期 run と同じ契約で更新検知、state 更新、Daily notification、run report を実行する。

⸻

6.2 基本手順

Discord 上で、本文がちょうど以下になるメッセージを送る。
```text
fetch
```

期待される結果
	•	受理されたことが分かる初期応答が返る
	•	詳細結果は Daily notification または run report で確認できる
	•	run 完了後、更新有無に応じた通知が行われる

⸻

6.3 fetch 実行後の確認順

fetch 実行後は、以下の順で確認する。
	1.	初期応答が返っているか
	2.	run report が送られたか
	3.	更新があれば Daily notification が送られたか
	4.	delivery failure が出ていないか
	5.	latest で保存済み state が反映されているか

⸻

6.4 fetch の注意点
	•	fetch は write path であり、state を更新しうる
	•	fetch は定期 run の代替ではないが、定期 run と同じ経路で確認できる
	•	同時実行自体は許容される
	•	ただし、state が壊れることは許容されない
	•	fetch を連打した場合でも、同一話の再通知が発生しないことが期待される

⸻

7. Daily notification の見方

7.1 確認ポイント

Daily notification では以下を確認する。
	•	更新があった run のときだけ送られているか
	•	1 run の更新が 1 通に集約されているか
	•	各行に「作品名」「新しい最新話」「前回話」があるか
	•	watchlist 順で並んでいるか
	•	長いエピソード名が極端に読みにくくなっていないか
	•	同一話が重複して通知されていないか

⸻

7.2 異常の兆候
	•	更新がないのに Daily notification が送られる
	•	同じ work_id + latest_key の通知が再度届く
	•	metadata 更新だけで通知が飛ぶ
	•	ラベルの切り詰めが崩れている
	•	URL があるのに link になっていない
	•	作品順が watchlist 順になっていない

⸻

8. run report の見方

8.1 目的

run report は、毎 run の結果を把握するための主要な運用面である。
更新有無にかかわらず送られ、少なくとも以下を区別できる必要がある。
	•	更新がなかった
	•	run が失敗した
	•	更新はあったが delivery に失敗した

⸻

8.2 確認ポイント
	•	実行時刻があるか
	•	trigger source が分かるか
	•	更新件数が分かるか
	•	Daily notification 送信有無が分かるか
	•	source failure / run-level failure の要約があるか
	•	状態要約が分かるか
	•	「更新なし」と「失敗」が混同されていないか
	•	delivery failure が見えなくなっていないか

⸻

8.3 run report からの切り分け

更新なし
	•	run 自体は成立している
	•	更新件数 0
	•	failure なし、または更新なしと矛盾しない範囲

source failure
	•	一部作品の取得に失敗している
	•	他作品は成功している可能性がある
	•	latest は保存済み state を返す

run-level failure
	•	state save failure
	•	watchlist/state load failure
	•	run 自体の成立に影響する failure

delivery failure
	•	更新検知は成功している
	•	ただし通知送信が一部または全部失敗している
	•	再送対象が残っている可能性が高い

⸻

9. delivery failure の確認と再送

9.1 まず確認すること

delivery failure が見えた場合は、以下を順に確認する。
	1.	run report に更新ありと出ているか
	2.	Daily notification が届かなかったのか、一部だけ届かなかったのか
	3.	delivery failure の要約が出ているか
	4.	pending 再送対象が保持されているか
	5.	backend 側の障害か、設定異常かを切り分けられるか

⸻

9.2 再送時の基本方針
	•	delivery failure は「更新なし」ではない
	•	更新検知結果を捨てず、再送可能状態を維持することが前提である
	•	再送は次回 run または replay 処理で行う
	•	duplicate は consumer 側の event_id dedupe を前提に扱う

⸻

9.3 再送確認の観点
	•	pending 対象が残っているか
	•	pending backend が減っていくか
	•	再送成功後に保留状態が解消されるか
	•	same event の stable id が維持されているか
	•	delivery failure が再び「更新なし」と誤認されていないか

⸻

10. state 異常時の確認

10.1 最優先確認事項

state に異常が疑われる場合、最初に確認するのは以下とする。
	1.	state ファイルが JSON として読めるか
	2.	reader が parse error を起こしていないか
	3.	直前に異常終了や同時実行が発生していないか
	4.	state save failure が run report に出ていないか

⸻

10.2 典型的な兆候
	•	latest が突然失敗し始めた
	•	run report で state save failure が出ている
	•	同じ作品の表示が不自然に戻る
	•	unread や latest の整合が崩れる
	•	parse error が出る

⸻

10.3 切り分け手順
	1.	state ファイルを JSON として読めるか確認する
	2.	直近 run report を確認する
	3.	失敗が source failure か run-level failure か確認する
	4.	delivery failure ではなく persistence failure であることを確認する
	5.	同時実行や異常終了の痕跡がないか確認する
	6.	必要に応じて latest と run report の差分を見る

⸻

10.4 重要な判断基準
	•	state が JSON として読めない場合は重大障害として扱う
	•	state 破損は運用で吸収せず、受け入れ不適合または実装修正対象とする
	•	一時的な source failure は state 破損とは区別して扱う

⸻

11. デバッグの基本手順

11.1 まず見る順番

不具合や違和感が出た場合は、以下の順で確認する。
	1.	run report
	2.	Daily notification の有無
	3.	latest の表示
	4.	state の JSON 可読性
	5.	delivery failure の有無
	6.	source failure / run-level failure の別
	7.	必要に応じて詳細ログ

⸻

11.2 よくある症状別の見方

症状: 更新があるはずなのに通知が来ない

確認順:
	1.	run report に更新ありと出ているか
	2.	delivery failure が出ていないか
	3.	metadata 更新扱いになっていないか
	4.	dedupe が効いているだけではないか

症状: 同じ通知がまた来た

確認順:
	1.	work_id + latest_key が同一か
	2.	replay による再送ではないか
	3.	consumer 側 dedupe が期待どおりか
	4.	実際に Daily notification が重複生成されていないか

症状: latest が変だが通知は正常

確認順:
	1.	latest が保存済み参照であることを再確認する
	2.	state.latest の内容を確認する
	3.	stale / partial failure warning の有無を見る
	4.	直近 run report と食い違いがないか確認する

症状: run report が来ない

確認順:
	1.	run 自体が起動しているか
	2.	Discord delivery failure ではないか
	3.	run-level failure が起きていないか
	4.	設定異常や token / webhook 周りに問題がないか

⸻

11.3 ログ確認時の注意
	•	token や webhook URL が出ていないことを確認する
	•	error message に秘匿情報が混入していないことを確認する
	•	source failure と run-level failure を混同しない
	•	delivery failure と更新なしを混同しない

⸻

12. Discord 実機確認手順

12.1 位置づけ

Discord 実機確認は、主たる受け入れ判定ではなく補助的な確認である。
主判定はモックベース自動試験で行い、実機確認は表示差異や回帰検知を目的とする。

⸻

12.2 実機確認の対象

少なくとも以下の代表ケースを確認対象とする。
	•	latest の通常ケース
	•	latest の未取得ケース
	•	Daily notification の単一更新ケース
	•	Daily notification の複数更新ケース
	•	run report の更新なしケース
	•	run report の failure ケース

⸻

12.3 実機確認の観点
	•	改行が崩れていないか
	•	link が期待どおり表示されるか
	•	全角コロン ： や矢印 ← が崩れないか
	•	省略記号 … が崩れないか
	•	行順が watchlist 順のままか
	•	想定外 mention が発生していないか
	•	モバイル端末で見て読みにくくないか

⸻

12.4 実機確認の運用ルール
	•	本番チャンネルではなく test guild / test channel を使う
	•	実機自動確認は flaky になりうるため、主受け入れとは分離して扱う
	•	補助 E2E は `python -m manga_watch.discord_real_e2e --case all --json` を test guild で実行し、差異が出たら先に mocked acceptance と formatter / builder の構造契約を見る
	•	実機確認で見つかった表示差異は formatter / builder 修正候補として扱う
	•	実機結果だけで契約違反と断定せず、まずモック試験との差分を見る

⸻

13. 運用上の判断基準まとめ

13.1 すぐ対応すべきもの
	•	state が JSON として読めない
	•	run report が継続的に来ない
	•	delivery failure が継続して解消されない
	•	同一話の再通知が継続発生する
	•	token / webhook URL の露出が疑われる

13.2 影響を見ながら対応するもの
	•	source failure が一部作品で断続的に起きる
	•	truncate の見た目が少し悪い
	•	実機表示差異が軽微
	•	benchmark が目標未達だが機能契約は守れている

⸻

14. 定期チェックリスト

日常運用では、以下を定期的に確認する。
	•	run report が継続して届いている
	•	更新なしと failure が明確に区別されている
	•	delivery failure が滞留していない
	•	latest が極端に stale になっていない
	•	Daily notification が重複していない
	•	ログに秘匿情報が露出していない
	•	test guild の実機確認が大きく崩れていない

⸻

15. 付記

本手順書は、受け入れ仕様書と設計書に従って更新される。
外部契約が変わる場合は SPEC.md を先に更新し、内部方式が変わる場合は設計書を先に更新する。
本手順書は、その変更が運用上どのように扱われるかを反映する。

16. GitHub Container Registry 公開フローの動作確認

16.1 目的
	•	`main` への push を契機に Docker image が GHCR (`ghcr.io/<owner>/<repo>`) に publish されることを確認する
	•	手動実行時は `push_image` 入力で「ビルド確認のみ（push なし）」と「実際に publish」を切り替えられることを確認する

16.2 事前確認
	•	GitHub Actions が有効であること
	•	repository の `GITHUB_TOKEN` で packages:write が許可されること
	•	`Dockerfile` と `requirements.txt` が最新であること

16.3 手動実行での確認（推奨: 先に dry-run）
	1.	GitHub の `Actions` タブから `Publish Container Image` を選ぶ
	2.	`Run workflow` で対象 branch を選ぶ
	3.	`push_image=false` で実行し、`Build and push container image` が成功することを確認する（このとき GHCR には push されない）
	4.	必要に応じて `push_image=true` で再実行し、GHCR に image が登録されることを確認する

16.4 main push での確認
	1.	`main` に commit を push する
	2.	`Publish Container Image` workflow が自動起動することを確認する
	3.	workflow 成功後、`Packages` 画面で `latest` と short SHA tag が更新されていることを確認する

16.5 失敗時の切り分け
	•	login step 失敗: `packages: write` 権限と org/repo の package policy を確認する
	•	build step 失敗: `Dockerfile` / 依存パッケージ更新の影響を確認する
	•	tag 不整合: `docker/metadata-action` の tag 生成ルールを確認する
