# 受け入れテスト計画書

## 1. 目的

本書は、`comic_crawler` の受け入れ仕様書（`SPEC.md`）に定義された契約を、どのような試験で確認するかを定義する。  
本書の目的は、受け入れ担当・実装担当・レビュー担当が同じ観点で合否判定できるようにすること、および主要な品質条件を自動試験で継続確認できるようにすることである。

本書では、以下を明確にする。

- 何を必須試験とするか
- 何を目標値確認とするか
- どの試験を自動化対象とするか
- Discord 実機確認をどの位置づけで扱うか
- 合否判定の基準をどう置くか

---

## 2. 基本方針

### 2.1 主判定は自動試験とする
主要な受け入れ条件は、自動試験で判定可能でなければならない。  
人手による確認は補助的に位置づけ、主要合否判定の中心には置かない。

### 2.2 モック試験を主、実機試験を従とする
Discord に関する試験は、以下の二層で扱う。

- 主判定: モックベース自動試験
- 補助判定: 実機自動 E2E または手動 smoke

### 2.3 必須条件と目標値を分ける
機能契約と安全性契約は必須条件とする。  
性能値や実機表示の一部品質は目標値または補助確認とする。

### 2.4 state 安全性を最優先とする
state が JSON として壊れないこと、reader が読めない中間状態を見ないことは、最優先の必須条件とする。

---

## 3. テストレイヤ構成

## 3.1 Unit / Formatter tests

対象:
- `latest` message builder
- Daily notification builder
- run report builder
- fallback rules
- truncate rules

目的:
- 文面構造・情報順・表記ルールを高速に検証する
- 小さな変更が UX 契約を壊していないかを即時に検出する

---

## 3.2 Service / Orchestration tests

対象:
- `latest` read-only 性
- `fetch` write path
- checker と runner の連携
- dedupe
- silent merge
- run report の意味区別
- delivery failure 可視化

目的:
- 外部契約単位の挙動を検証する
- business logic の主要契約をまとめて確認する

---

## 3.3 Persistence / Crash tests

対象:
- state 保存中の異常終了
- concurrent reader
- concurrent writer
- replace ベース保存
- JSON integrity

目的:
- 最重要要件である state 安全性を検証する
- 実運用上もっとも危険な破損リスクを潰す

---

## 3.4 Mocked Discord integration tests

対象:
- Discord adapter の inbound / outbound
- `latest` 応答生成
- `fetch` 受理応答
- Daily notification 送信 payload
- run report 送信 payload
- failure handling

目的:
- Discord surface の契約を安定して自動検証する
- 実機の不安定要素なしに受け入れ主判定を行う

---

## 3.5 Real Discord E2E harness

対象:
- test guild / test channels / test bot を用いた実送信
- 投稿内容取得
- 改行、リンク、全角記号、行順の確認
- 想定外 mention が発生しないことの確認

目的:
- Discord 実表示差異の回帰検知
- モックでは拾いにくいレンダリング差分の補足確認

位置づけ:
- 補助的検証
- 主受け入れ判定ではない

---

## 4. 合否判定ルール

## 4.1 必須条件

以下を満たさない場合、受け入れ NG とする。

- `latest` が read-only である
- `latest` が live crawl を起動しない
- Daily notification が `work_id + latest_key` 基準で重複しない
- metadata 改善のみでは Daily notification を送らない
- run report が毎 run 生成される
- run report で「更新なし」「run failure」「delivery failure」が区別できる
- state が異常終了後も JSON として読める
- 書き込み中に reader が parse error を起こさない
- token / webhook URL がログ・report・error 出力に露出しない
- `latest` / Daily notification の生成文面が構造・情報順・表記ルールを満たす

---

## 4.2 目標条件

未達でも即受け入れ NG ではないが、記録して改善対象とする。

- watchlist 100 件で 30 秒以内
- Discord 初期応答 3 秒以内
- `latest` 本応答 10 秒以内
- 高頻度並列実行時の劣化が許容範囲内
- 実機表示がモック結果と整合する

---

## 4.3 参考条件

あると望ましいが、初回受け入れ必須とはしない。

- Discord 実機自動 E2E の常時運用
- モバイル表示の自動視覚比較
- より大規模件数での benchmark 継続運用
- fault injection の高度化

---

## 7. テストデータ方針

- watchlist 順が明確な固定データを用意する
- URL あり / URL なし / title 欠損 / code 欠損 / 未取得を含む
- `latest_key` 不変の metadata 改善ケースを必ず持つ
- delivery failure / source failure / run-level failure の各種疑似ケースを持つ
- 並列試験用の再現可能な入力セットを持つ
- 秘匿情報露出試験用にダミー token / webhook URL を持つ

## 8. テストレポート方針

各試験実行では少なくとも以下を残す。

- 実行日時
- 対象ブランチまたは commit
- 実行したテスト群
- 成功 / 失敗 / スキップ件数
- Must / Should / Nice-to-have ごとの結果
- benchmark 結果
- 失敗ケースの要約

## 9. 受け入れ判定テンプレート

### 9.1 判定項目

- 必須条件をすべて満たしたか
- 目標条件の測定結果を記録したか
- 実機補助検証で重大差異が出ていないか
- 未解決の重大リスクが残っていないか

### 9.2 判定結果

- **Accept**: 必須条件を満たす
- **Conditional Accept**: 必須条件は満たすが Should に重大未達があり、改善計画付き
- **Reject**: 必須条件の未達がある
