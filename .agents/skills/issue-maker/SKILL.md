# Issue Maker

## Overview

この skill は、ユーザーの曖昧な要求をそのまま解決策に飛ばさず、要件の抜け・矛盾・前提漏れを見つけながら、実行可能な要件定義のたたき台に整理する。
質問を増やすこと自体が目的ではない。毎ターン「今いちばん方向性を明確にする質問」を優先し、要求の判断材料を増やす。

## Workflow

### 1. 現時点の理解を短く要約する

- ユーザーの説明を読んだら、まず理解した内容を 3 行以内で要約する。
- 解決策の提案ではなく、今わかっている要求、目的、対象、期待値を短く言い直す。
- 推測が混ざる場合は断定せず、「現時点ではこう理解している」と置く。

見出しは必ず `現時点の理解` とする。

### 2. 次に確認すべき質問を 3〜7 個に絞る

- 質問数は一度に増やしすぎない。原則 3〜7 個に絞る。
- 重要度順に並べる。最初の数問で方向性が大きく変わる論点を優先する。
- 各質問には必ず `確認理由` を一言添える。
- 単なる思いつきで広げず、要件の判断に効く質問だけを残す。

見出しは必ず `確認したい質問` とし、番号付きで出す。

各質問の書き方は次の形に揃える。

```markdown
1. 質問文
   確認理由: ...
```

### 3. まず詰めるべき観点を優先する

次の観点が不明なら、優先して質問する。

- 背景・目的
- 誰のための要求か
- 解決したい課題
- 成功条件・評価指標
- スコープ / 非スコープ
- 制約条件
- 業務フローや現行運用
- 例外ケース・失敗時の扱い
- 非機能要件
- 意思決定者とレビュー観点

全部を毎回聞く必要はない。欠けているもののうち、いま最も判断に効くものから聞く。

### 4. 曖昧な表現を具体化する

ユーザーの発言に次のような抽象語があれば、その意味を定義する質問に置き換える。

- 良い
- 使いやすい
- 早い
- 効率的
- 柔軟
- 安全
- 安定

例:

- `使いやすくしたい` と言われたら、誰にとって何が楽になる状態を指すのかを聞く。
- `早くしたい` と言われたら、何の処理をどの程度短縮したいのかを聞く。

### 5. 要求と解決策を切り分ける

- ユーザーが特定の実装案やツール名を先に出していても、それが本当に要求なのか、単なる候補なのかを切り分ける。
- 「何を達成したいか」と「どう実現するか」が混ざっていそうなら、その差を質問で分離する。
- 解決策の議論に入る前に、目的・制約・成功条件が言語化できる状態を作る。

### 6. 不足が減るまで対話を続ける

- ユーザーの回答を受けたら、残る不確実性を評価して次の質問を続ける。
- 細部に入りすぎて進行を止めない。未確定のままでも進められる項目は `未確定事項 / 要確認事項` に逃がす。
- 情報が十分にそろったら、質問フェーズを止めて要件定義のたたき台にまとめる。

要件整理に進んでよい目安:

- 目的と解決したい課題が説明できる
- 主な対象ユーザーと関係者が説明できる
- 成功条件とスコープの仮説がある
- 大きな制約と未確定事項が明示できる

## Output Contract

各ターンの基本出力は次の順番に固定する。

1. `現時点の理解`
2. `確認したい質問`
3. 必要なら `現時点で見えている曖昧さ・リスク`

`現時点で見えている曖昧さ・リスク` は、方向性に影響する論点があるときだけ 2〜5 件の箇条書きで出す。

## Final Summary Format

情報が十分に集まったら、最後に次の形式で整理する。

- 要求の要約
- 解決したい課題
- 目的
- 対象ユーザー / 関係者
- スコープ
- 非スコープ
- 機能要件
- 非機能要件
- 制約条件
- 前提
- 未確定事項 / 要確認事項
- リスク
- 次に決めるべきこと

## Guardrails

- 思い込みで補完しすぎない。不明な点は確認する。
- ただし、細かすぎる質問で進行を止めない。
- いま重要でない論点より、方向性を左右する論点を先に聞く。
- ユーザーの言葉をそのまま鵜呑みにせず、曖昧さ、不足、矛盾、前提漏れを探す。
- 回答は基本的にユーザーの言語に合わせる。日本語で来たら日本語で返す。
